## 2. Critical Issues

### 2.1 — Duplicated CHECK constraint for `statut_autorite` (factor now — confirmed with tech lead)

`db/model_item.sql` defines the same value list twice, byte-for-byte:

```sql
-- line 210-212 (CREATE TABLE)
statut_autorite text
    check (statut_autorite is null
           or statut_autorite in ('organisme_controle', 'ca', 'gestionnaire_materiel')),

-- line 251-253 (backfill ALTER for already-provisioned databases)
add column if not exists statut_autorite text
    check (statut_autorite is null
           or statut_autorite in ('organisme_controle', 'ca', 'gestionnaire_materiel'));
```

They are in sync today, but nothing enforces that a future addition to one list is mirrored in the other — a silent drift would let a value be accepted on a freshly-provisioned database and rejected (or vice versa) on an upgraded one, depending on which code path a given environment took. This is exactly the kind of invariant that should live in one place.

**What happens if this runs twice?** No issue by itself (the ALTER is `if not exists`), but a *second* migration file editing only one of the two copies is what actually breaks — and nothing would catch it until a specific environment hit the discrepancy.

**Requested fix:** factor the value list into a single source of truth before merge — e.g. a `domain check` (`create domain public.statut_autorite_t as text check (...)`) referenced from both places, or drop the backfill copy entirely and have it reference the same constant. Given this is a one-time backfill block for pre-existing databases, the domain-type approach is the cleanest: define `create domain` once near the top of `model_item.sql`, use it for the column type in both the `CREATE TABLE` and the `ALTER TABLE ... ADD COLUMN`.

### 2.2 — Automatic-bascule reason string does not identify which counter is overdue (confirmed with tech lead)

`public.item_bouteille_appliquer_hors_validite()` (`db/item_bouteille.sql:411-438`) always writes the same generic reason:

```sql
statut_motif = 'Échéance de contrôle dépassée (bascule automatique)',
```

`echeance_min` — the value actually driving the bascule — can come from either the optical or the hydraulic counter (`v_item_bouteille.echeance_min`, §10.3), and the two are tracked as genuinely independent facts throughout the rest of the design (separate columns, separate periodicities, separate NULL semantics). The reason recorded in `item_transition`/`audit_log` for this automatic transition should say which one triggered it — an operator reading the audit trail six months later has no way to tell without re-deriving it from `v_item_bouteille`, and by then the overdue counter may have been updated and no longer show as the cause.

**Requested fix:** compute which counter is responsible per candidate row and interpolate it into `statut_motif`, e.g.:

```sql
with candidats as (
    select i.id,
        case
            when b.echeance_optique is not null and b.echeance_optique < p_a_la_date
                 and (b.echeance_hydraulique is null or b.echeance_optique <= b.echeance_hydraulique)
            then 'optique'
            else 'hydraulique'
        end as controle_en_cause
    from public.item i
    join public.v_item_bouteille b on b.item_id = i.id
    where i.actif
      and i.statut_code in ('en_stock', 'en_attente_controle', 'prete')
      and b.echeance_min is not null
      and b.echeance_min < p_a_la_date
)
update public.item i
set statut_code = 'hors_validite',
    statut_motif = format('Échéance de contrôle %s dépassée (bascule automatique)', c.controle_en_cause),
    statut_date_effet = p_a_la_date
from candidats c
where i.id = c.id;
```

Adjust the tie-break rule with the tech lead if both counters can be overdue simultaneously and there's a preferred wording for that case (e.g. "optique et hydraulique").

## 3. Recommended Improvements

### 3.1 — `bouteille_periodicite_mois` / `bouteille_tarif_apragaz` silently return the same value forever if a referential row is inserted with a past `date_effet` behind an already-in-force one out of order

Not a bug given the current INSERT-only, admin-gated write path (RLS requires `referentiel.create`), but worth a one-line comment: the "in force" resolution (`order by date_effet desc limit 1`) trusts insertion order to reflect chronological intent only through `date_effet`, which is correct — no action needed, just flagging that this is the *only* correctness guarantee (there's no check preventing an admin from inserting a `date_effet` far in the past, which would be silently ignored by `bouteille_echeance()` for controls performed today but could still be picked up for historical controls whose date falls after it). Confirm this is acceptable (append-only history editing, not just append-only forward-dating).

### 3.2 — `item_bouteille_appliquer_hors_validite()` uses `i.actif` as a guard but doesn't exclude items whose `statut_code` is already a terminal status reachable outside the whitelist

Currently safe because the `WHERE i.statut_code in ('en_stock', 'en_attente_controle', 'prete')` whitelist already excludes every other status, terminal or not — this is a purely defensive note, not a bug: if a new non-terminal status is ever added to `ref_statut` without updating this whitelist, it would simply never be considered for the automatic bascule (fails safe), not the other way around. No change requested.

### 3.3 — Consider a `NOT NULL` or trigger-level guard on `ref_periodicite_bouteille.cree_par` / `ref_tarif_apragaz.cree_par`

Both are nullable `uuid`, populated presumably from `auth.uid()` by the calling application code (not shown in this diff — no `default` clause, no trigger). If nothing sets it, every admin-inserted referential row will have `cree_par = NULL`, which weakens the audit value of this append-only history (you'd know *what* changed and *when*, not *who*). Confirm whether the WASM insert path is expected to set it explicitly, or add `default auth.uid()`.

## 5. Tests to Add

- **Both counters simultaneously overdue** on the same bascule pass: assert the (post-fix) `statut_motif` correctly reflects both, or the agreed tie-break wording — currently untested because the fix in §2.2 doesn't exist yet.
- **Retroactive/out-of-order `date_effet` insert** (§3.1): insert a `ref_periodicite_bouteille` row with a `date_effet` in the past that is *older* than a currently-in-force row, and assert `bouteille_periodicite_mois` still resolves the row with the latest `date_effet <= p_a_la_date` — pins down the "in force" resolution rule the SQL comment already documents in prose.
- **Concurrent invocation of `item_bouteille_appliquer_hors_validite()`**: two overlapping calls (e.g. via two `psql` sessions or `pg_advisory_lock`-free concurrent transactions) against the same overdue item should not double-log a transition — worth at least one CI test asserting `item_transition` gets exactly one row even under a race, since the function has no explicit locking of its own (it currently relies on standard row-level UPDATE locking + `WHERE` re-evaluation under READ COMMITTED, which should be safe, but this is exactly the kind of "what if this runs twice" case the review grid asks to challenge and it is not exercised today).
- **`CylinderReferenceType.Resolve` with an unrecognized `CylinderMaterial` code** for the `Diving` family is already covered indirectly by the `switch` default branch, but there is no explicit unit test constructing a bogus/synthetic material to hit the `_ => throw` arm (the sealed-record factory pattern makes this hard to reach today, which is good, but a regression that added a new `CylinderMaterial` without updating the switch would only be caught by this default branch — add a test if a reflection-free way to construct one exists, otherwise a comment noting the exhaustiveness is enforced structurally, not by a test, is enough).
