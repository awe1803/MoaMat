La modélisation métier et le moteur SQL sont tous deux bien pensés : référentiels historisés en append-only, deux compteurs calculés indépendamment sans aucune alternance codée en dur, miroir C# pur du moteur SQL maintenu synchrone et testé unitairement jusque dans la sémantique d'arithmétique de dates propre à PostgreSQL, et une bascule automatique `SECURITY DEFINER` qui réutilise correctement le trigger de machine à états existant plutôt que d'en dupliquer la logique. - le libellé du motif de bascule automatique n'est pas assez précis pour la piste d'audit qu'il alimente (`item_transition` / `audit_log`) ;

## 2. Problèmes critiques

### 2.1 — Contrainte CHECK de `statut_autorite` dupliquée (à factoriser maintenant — confirmé avec le tech lead)

`db/model_item.sql` définit deux fois la même liste de valeurs, à l'identique :

```sql
-- ligne 210-212 (CREATE TABLE)
statut_autorite text
    check (statut_autorite is null
           or statut_autorite in ('organisme_controle', 'ca', 'gestionnaire_materiel')),

-- ligne 251-253 (ALTER de rattrapage pour les bases déjà provisionnées)
add column if not exists statut_autorite text
    check (statut_autorite is null
           or statut_autorite in ('organisme_controle', 'ca', 'gestionnaire_materiel'));
```

Elles sont synchronisées aujourd'hui, mais rien n'impose qu'un futur ajout dans l'une soit répercuté dans l'autre — une divergence silencieuse permettrait à une valeur d'être acceptée sur une base fraîchement provisionnée et refusée (ou l'inverse) sur une base migrée, selon le chemin de code emprunté par tel ou tel environnement. C'est exactement le type d'invariant qui doit vivre à un seul endroit.

**Que se passe-t-il si ceci s'exécute deux fois ?** Pas de problème en soi (l'ALTER est `if not exists`), mais c'est une *seconde* migration modifiant une seule des deux copies qui casse réellement les choses — et rien ne le détecterait avant qu'un environnement précis ne rencontre l'écart.

**Correction demandée :** factoriser la liste de valeurs en une seule source de vérité avant la fusion — par exemple un `domain` PostgreSQL (`create domain public.statut_autorite_t as text check (...)`) référencé aux deux endroits, ou supprimer la copie de rattrapage et la faire référencer la même constante. Comme il s'agit d'un bloc de rattrapage ponctuel pour bases préexistantes, l'approche par `domain` est la plus propre : le définir une fois en tête de `model_item.sql`, puis l'utiliser comme type de colonne à la fois dans le `CREATE TABLE` et dans le `ALTER TABLE ... ADD COLUMN`.

### 2.2 — Le motif de bascule automatique n'identifie pas quel compteur est dépassé (confirmé avec le tech lead)

`public.item_bouteille_appliquer_hors_validite()` (`db/item_bouteille.sql:411-438`) écrit toujours le même motif générique :

```sql
statut_motif = 'Échéance de contrôle dépassée (bascule automatique)',
```

`echeance_min` — la valeur qui déclenche réellement la bascule — peut provenir soit du compteur optique, soit de l'hydraulique (`v_item_bouteille.echeance_min`, §10.3), et les deux sont traités comme des faits réellement indépendants partout ailleurs dans la conception (colonnes séparées, périodicités séparées, sémantique NULL séparée). Le motif enregistré dans `item_transition`/`audit_log` pour cette transition automatique devrait préciser lequel des deux l'a déclenchée — un opérateur qui relit la piste d'audit six mois plus tard n'a aucun moyen de le savoir sans re-dériver l'information depuis `v_item_bouteille`, et à ce moment-là le compteur en cause peut déjà avoir été mis à jour et ne plus apparaître comme la cause.

**Correction demandée :** calculer, pour chaque ligne candidate, quel compteur est en cause et l'interpoler dans `statut_motif`, par exemple :

```sql
with candidats as (
    select i.id,
        case
            when b.echeance_optique is not null and b.echeance_optique < p_a_la_date
                 and (b.echeance_hydraulique is null or b.echeance_optique <= b.echeance_hydraulique)
            then 'optique'
            else 'hydraulique'
        end as controle_en_cause
    from public.item i
    join public.v_item_bouteille b on b.item_id = i.id
    where i.actif
      and i.statut_code in ('en_stock', 'en_attente_controle', 'prete')
      and b.echeance_min is not null
      and b.echeance_min < p_a_la_date
)
update public.item i
set statut_code = 'hors_validite',
    statut_motif = format('Échéance de contrôle %s dépassée (bascule automatique)', c.controle_en_cause),
    statut_date_effet = p_a_la_date
from candidats c
where i.id = c.id;
```

À ajuster avec le tech lead pour la règle de priorité si les deux compteurs peuvent être dépassés simultanément et qu'il existe un libellé préféré pour ce cas (ex. « optique et hydraulique »).

## 3. Améliorations recommandées

### 3.1 — `bouteille_periodicite_mois` / `bouteille_tarif_apragaz` retournent silencieusement la même valeur si une ligne référentielle est insérée avec un `date_effet` passé, en retard sur une ligne déjà en vigueur

Pas un bug compte tenu du chemin d'écriture actuel (INSERT seul, réservé admin, RLS via `referentiel.create`), mais mérite un commentaire d'une ligne : la résolution « en vigueur » (`order by date_effet desc limit 1`) fait confiance à `date_effet` seul pour refléter l'intention chronologique, ce qui est correct — aucune action requise, simple signalement que c'est la *seule* garantie de correction (rien n'empêche un admin d'insérer un `date_effet` très ancien, ignoré silencieusement par `bouteille_echeance()` pour les contrôles d'aujourd'hui mais potentiellement repris pour des contrôles historiques dont la date se situe après). À confirmer que c'est voulu (réécriture de l'historique possible, pas uniquement de la datation en avant).

### 3.2 — `item_bouteille_appliquer_hors_validite()` s'appuie sur `i.actif` mais n'exclut pas explicitement les statuts déjà terminaux hors liste blanche

Sans risque actuellement car le `WHERE i.statut_code in ('en_stock', 'en_attente_controle', 'prete')` exclut déjà tout autre statut, terminal ou non — remarque purement défensive, pas un bug : si un nouveau statut non terminal est ajouté un jour à `ref_statut` sans mettre à jour cette liste blanche, il serait simplement jamais candidat à la bascule automatique (échoue de façon sûre), jamais l'inverse. Aucun changement demandé.

### 3.3 — Envisager une garde `NOT NULL` ou au niveau trigger sur `ref_periodicite_bouteille.cree_par` / `ref_tarif_apragaz.cree_par`

Les deux sont des `uuid` nullables, censés être renseignés depuis `auth.uid()` par le code applicatif appelant (non visible dans ce diff — pas de clause `default`, pas de trigger). Si rien ne le renseigne, chaque ligne référentielle insérée par un admin aura `cree_par = NULL`, ce qui affaiblit la valeur d'audit de cet historique append-only (on saura *ce qui* a changé et *quand*, pas *qui*). À confirmer : le chemin d'insertion côté WASM est-il censé le renseigner explicitement, ou faut-il ajouter `default auth.uid()` ?
