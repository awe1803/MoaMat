# Code Review — Cylinders (Bouteilles) business engine

**Scope reviewed:** `db/item_etat.sql` (diff), `db/model_item.sql` (diff), `db/MODELE.md` (diff), `db/item_bouteille.sql` (new), `db/tests/item_bouteille_tests.sql` (new), `src/MoaMat.Domain/Cylinders/*` (new), `tests/MoaMat.UnitTests/Cylinders/*` (new).

---

## 1. Verdict

⚠️ **Risky** — the domain modeling and the SQL business logic (two independent due-date counters, historized/append-only referentials, automatic status bascule reusing the existing state-machine trigger) are solid and well tested. But there is one real production-safety gap around the `statut_autorite_t` domain migration, and one domain-naming collision that will cause confusion. Neither blocks merging outright, but both need to be resolved before this reaches an already-provisioned environment.

---

## 2. Critical Issues

### 2.1 The `statut_autorite_t` domain migration silently no-ops on any already-provisioned database

`db/model_item.sql` and `db/item_etat.sql` change `public.item.statut_autorite` and `public.item_transition.autorite_decision` from an inline `text check (... in (...))` column to a shared domain `public.statut_autorite_t`, explicitly to avoid the two CHECK lists silently diverging (the file's own comment says so).

The problem: the state-machine feature (`item_etat.sql`) was already merged in PR #41. Any environment that ran that version already has both columns as plain `text check(...)`. The only rework mechanism offered here is:

```sql
alter table public.item
    add column if not exists statut_autorite public.statut_autorite_t;
```

and, for `item_transition`, nothing at all beyond `create table if not exists` (which is a full no-op once the table exists).

`ADD COLUMN IF NOT EXISTS` **does not retype an existing column** — it just skips the clause. So on any database that already ran the old `item_etat.sql`/`model_item.sql` (staging, prod, or any dev DB that isn't rebuilt from scratch), both columns silently keep their old inline `text check(...)` definition forever. The new domain only actually applies on a brand-new database.

This is exactly the failure mode the migration's own comment warns against: the two constraints ("old" on already-provisioned DBs, "new domain" on fresh ones) can now diverge without any error, and a future edit to the domain's allowed values will only reach fresh databases.

**Fix:** add an explicit retyping step for both columns, guarded so it's a no-op when already applied, e.g.:

```sql
do $$
begin
    if exists (
        select 1 from information_schema.columns
        where table_schema = 'public' and table_name = 'item'
          and column_name = 'statut_autorite' and data_type = 'text'
    ) then
        alter table public.item drop constraint if exists item_statut_autorite_check;
        alter table public.item alter column statut_autorite type public.statut_autorite_t;
    end if;
end $$;
```
(and the equivalent for `public.item_transition.autorite_decision`, plus dropping whatever the old inline check's auto-generated constraint name is).

**What happens if this runs twice?** Fine — no-op once the type is already the domain. **What happens on the already-migrated staging/prod DB today?** Nothing — the domain is created, but neither column is ever actually converted to it, so the single-source-of-truth goal is not met there.

## 3. Recommended Improvements

### 3.1 `CylinderFamily` collides semantically with `ItemFamily.Cylinder`

`MoaMat.Domain.Inventory.ItemFamily.Cylinder` (code `"bouteille"`, backs `public.item.famille`) and the new `MoaMat.Domain.Cylinders.CylinderFamily.Diving` (code `"plongee"`, backs `public.item_bouteille.famille`) are two different concepts at two different levels of the model, both named around "family", both keyed on a column literally called `famille`. `CylinderFamily.Diving` is not "the family of a cylinder item" (that's always `ItemFamily.Cylinder`) — it's the *usage sub-classification* of a cylinder. The XML docs explain the distinction, but the type names don't, and a reader skimming call sites (`CylinderFamily.Diving`, `ItemFamily.Cylinder`) can easily conflate the two axes.

Suggest renaming to something that doesn't reuse "Family" verbatim for a different axis — e.g. `CylinderUsage` / `CylinderUsageFamily` / `CylinderProfile` — to keep the ubiquitous language unambiguous.

### 3.2 SQL vs. C# disagree on a missing material for a diving cylinder

- `public.bouteille_type_referentiel('plongee', null)` → `NULL` (silent, tolerant).
- `CylinderReferenceType.Resolve(CylinderFamily.Diving, material: null)` → throws `ArgumentException`.

Both are documented as "the same 6-profile resolver mirrored in two languages", but they don't behave the same way at this edge. If a UI ever builds a `CylinderFamily`/`CylinderMaterial` pair from partially-entered form state and calls `Resolve` before validation is complete, it will throw where the database would have quietly returned `NULL`/an unresolved due date. Either tighten the SQL side (raise on an invalid/incomplete pair) or soften the C# side (return `null`) — pick one behavior and keep both in sync, the same way the two engines are already kept in sync for the periodicity math.

### 3.3 `item.date_echeance` can go stale if an `item_bouteille` row is deleted

`tg_item_bouteille_sync_echeance` fires `after insert or update of famille, matiere, date_dernier_controle_optique, date_dernier_controle_hydraulique` — there is no `after delete` path. If a bouteille's classification row is ever removed (e.g. reclassifying an item out of the `bouteille` family), `public.item.date_echeance` keeps whatever value was last synced, which then feeds `item_est_disponible()` and the "by due date" filters with a stale date. Likely a rare operation today, but worth either a delete trigger that clears `date_echeance`, or an explicit note that this path is currently unsupported/out of scope.

### 3.4 Unvalidated `matiere`/`famille` strings passed directly into `bouteille_type_referentiel`

The function has no defensive check on its own — an unknown `matiere` (e.g. a typo reaching it outside the `item_bouteille` table's CHECK, such as a future ad-hoc query or report) silently resolves to a reference code that matches nothing in `ref_periodicite_bouteille`, and the due date becomes `NULL` — indistinguishable from "this control legitimately doesn't apply to this profile". Today this is safe because `item_bouteille.matiere`/`famille` are CHECK-constrained before they ever reach the function, but the function itself would benefit from failing loudly on an unrecognized pair, consistent with how the C# `CylinderReferenceType.Resolve` already does.

## 5. Tests to Add

- **Migration idempotency on a pre-existing column**: a test/script that creates `item.statut_autorite` as the *old* `text check(...)` shape, then replays the current `model_item.sql`, and asserts the column ends up typed as `public.statut_autorite_t` (this would currently fail — see §2.1).
- **`item_bouteille` row deleted**: assert whether `item.date_echeance` is cleared, kept, or explicitly documented as stale (currently untested either way).
- **Crash/duplicate-run scenarios for `item_bouteille_appliquer_hors_validite()`**: already covered well for "runs twice" (idempotent, 0 rows second time) — consider also a concurrent-invocation test (two sessions calling it at once) to confirm no double-transition/double-audit-row for the same item, given the function isn't wrapped in an explicit advisory lock.
- **`bouteille_type_referentiel` with an out-of-domain `matiere`** (e.g. `'titane'`): assert it resolves to `NULL`-propagating behavior today (documents the current, slightly fragile, contract) or add the guard from §3.4 and test that it raises instead.
- **C# `CylinderReferenceType.Resolve` vs. SQL `bouteille_type_referentiel` parity test** for the missing-material case, once §3.2 is resolved one way or the other.

## 6. Optional Refactoring

None with clear enough value to justify the churn right now — the append-only/historized referential pattern, the two-counter due-date engine, and the SECURITY DEFINER + `revoke`/`grant` guard on the automatic bascule are all consistent with the codebase's existing conventions (`item_transition`, `custom_access_token_hook`) and don't need rework, only the fixes above.
