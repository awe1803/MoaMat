# Revue de code — Moteur métier Bouteilles

**Périmètre revu :** `db/item_etat.sql` (diff), `db/model_item.sql` (diff), `db/MODELE.md` (diff), `db/item_bouteille.sql` (nouveau), `db/tests/item_bouteille_tests.sql` (nouveau), `src/MoaMat.Domain/Cylinders/*` (nouveau), `tests/MoaMat.UnitTests/Cylinders/*` (nouveau).

---

## 1. Verdict

⚠️ **Risqué** — la modélisation métier et la logique SQL (deux compteurs d'échéance indépendants, référentiels historisés/append-only, bascule automatique de statut réutilisant le trigger de machine à états existant) sont solides et bien testées. Mais il y a une vraie lacune de sécurité de production autour de la migration du domaine `statut_autorite_t`, et une collision de nommage métier qui va créer de la confusion. Aucune des deux n'empêche la fusion en soi, mais les deux doivent être résolues avant que ce code n'atteigne un environnement déjà provisionné.

---

## 2. Problèmes critiques

### 2.1 La migration du domaine `statut_autorite_t` ne s'applique silencieusement à AUCUNE base déjà provisionnée

`db/model_item.sql` et `db/item_etat.sql` font passer `public.item.statut_autorite` et `public.item_transition.autorite_decision` d'une colonne `text check (... in (...))` en ligne vers un domaine partagé `public.statut_autorite_t`, explicitement pour éviter que les deux listes CHECK ne divergent silencieusement (le commentaire du fichier le dit lui-même).

Le problème : la fonctionnalité de machine à états (`item_etat.sql`) a déjà été fusionnée dans la PR #41. Tout environnement ayant exécuté cette version possède déjà les deux colonnes en `text check(...)` simple. Le seul mécanisme de rattrapage proposé ici est :

```sql
alter table public.item
    add column if not exists statut_autorite public.statut_autorite_t;
```

et, pour `item_transition`, rien du tout au-delà de `create table if not exists` (qui est un no-op complet dès que la table existe déjà).

`ADD COLUMN IF NOT EXISTS` **ne change pas le type d'une colonne existante** — la clause est simplement ignorée. Donc sur toute base ayant déjà exécuté l'ancienne version de `item_etat.sql`/`model_item.sql` (staging, prod, ou toute base de dev qui n'est pas reconstruite de zéro), les deux colonnes conservent silencieusement pour toujours leur ancienne définition `text check(...)` en ligne. Le nouveau domaine ne s'applique en réalité que sur une base toute neuve.

C'est exactement le mode de défaillance que le commentaire de la migration met en garde contre lui-même : les deux contraintes (« ancienne » sur les bases déjà provisionnées, « nouveau domaine » sur les bases neuves) peuvent désormais diverger sans aucune erreur, et une future modification des valeurs autorisées du domaine n'atteindra que les bases neuves.

**Correctif :** ajouter une étape explicite de re-typage pour les deux colonnes, protégée pour être un no-op si déjà appliquée, par exemple :

```sql
do $$
begin
    if exists (
        select 1 from information_schema.columns
        where table_schema = 'public' and table_name = 'item'
          and column_name = 'statut_autorite' and data_type = 'text'
    ) then
        alter table public.item drop constraint if exists item_statut_autorite_check;
        alter table public.item alter column statut_autorite type public.statut_autorite_t;
    end if;
end $$;
```
(et l'équivalent pour `public.item_transition.autorite_decision`, en supprimant aussi le nom généré automatiquement de l'ancienne contrainte CHECK en ligne).

**Que se passe-t-il si ceci est rejoué deux fois ?** Rien de grave — no-op une fois le type déjà converti en domaine. **Que se passe-t-il aujourd'hui sur la base staging/prod déjà migrée ?** Rien — le domaine est créé, mais aucune des deux colonnes n'est jamais réellement convertie vers celui-ci, donc l'objectif de source unique n'y est pas atteint.

## 3. Améliorations recommandées

### 3.1 `CylinderFamily` entre en collision sémantique avec `ItemFamily.Cylinder`

`MoaMat.Domain.Inventory.ItemFamily.Cylinder` (code `"bouteille"`, porte `public.item.famille`) et le nouveau `MoaMat.Domain.Cylinders.CylinderFamily.Diving` (code `"plongee"`, porte `public.item_bouteille.famille`) sont deux concepts différents, à deux niveaux différents du modèle, tous les deux nommés autour de « family », tous les deux indexés sur une colonne littéralement appelée `famille`. `CylinderFamily.Diving` n'est pas « la famille d'un item bouteille » (c'est toujours `ItemFamily.Cylinder`) — c'est la *sous-classification d'usage* d'une bouteille. La documentation XML explique la distinction, mais pas les noms des types, et un lecteur qui parcourt les sites d'appel (`CylinderFamily.Diving`, `ItemFamily.Cylinder`) peut facilement confondre les deux axes.

Suggestion : renommer pour ne pas réutiliser « Family » à l'identique pour un axe différent — par exemple `CylinderUsage` / `CylinderUsageFamily` / `CylinderProfile` — afin de garder le langage omniprésent (ubiquitous language) sans ambiguïté.

### 3.2 Le SQL et le C# ne sont pas d'accord sur une matière manquante pour une bouteille de plongée

- `public.bouteille_type_referentiel('plongee', null)` → `NULL` (silencieux, tolérant).
- `CylinderReferenceType.Resolve(CylinderFamily.Diving, material: null)` → lève une `ArgumentException`.

Les deux sont documentés comme « le même résolveur à 6 profils, reproduit dans deux langages », mais ils ne se comportent pas de la même façon sur ce cas limite. Si une UI construit un jour un couple `CylinderFamily`/`CylinderMaterial` à partir d'un état de formulaire partiellement rempli et appelle `Resolve` avant la fin de la validation, elle lèvera une exception là où la base de données aurait tranquillement renvoyé `NULL`/une échéance non résolue. Soit durcir le côté SQL (lever une erreur sur un couple invalide/incomplet), soit assouplir le côté C# (renvoyer `null`) — choisir un seul comportement et garder les deux synchronisés, de la même façon que les deux moteurs sont déjà tenus synchronisés pour le calcul de périodicité.

### 3.3 `item.date_echeance` peut devenir obsolète si une ligne `item_bouteille` est supprimée

`tg_item_bouteille_sync_echeance` se déclenche `after insert or update of famille, matiere, date_dernier_controle_optique, date_dernier_controle_hydraulique` — il n'existe aucun chemin `after delete`. Si la ligne de classification d'une bouteille est un jour supprimée (par exemple en reclassant un item hors de la famille `bouteille`), `public.item.date_echeance` conserve la dernière valeur synchronisée, qui alimente ensuite `item_est_disponible()` et les filtres « par échéance » avec une date obsolète. Probablement une opération rare aujourd'hui, mais mérite soit un trigger de suppression qui vide `date_echeance`, soit une note explicite indiquant que ce chemin n'est actuellement pas pris en charge / hors périmètre.

### 3.4 Chaînes `matiere`/`famille` non validées passées directement à `bouteille_type_referentiel`

La fonction n'a aucun contrôle défensif propre — une `matiere` inconnue (par exemple une faute de frappe qui l'atteindrait hors de la contrainte CHECK de la table `item_bouteille`, via une future requête ad hoc ou un rapport) se résout silencieusement en un code réglementaire qui ne correspond à rien dans `ref_periodicite_bouteille`, et l'échéance devient `NULL` — indiscernable de « ce contrôle ne s'applique légitimement pas à ce profil ». Aujourd'hui c'est sans risque car `item_bouteille.matiere`/`famille` sont contraints par CHECK avant d'atteindre la fonction, mais la fonction elle-même gagnerait à échouer bruyamment sur un couple non reconnu, cohérent avec ce que fait déjà `CylinderReferenceType.Resolve` en C#.

## 5. Tests à ajouter

- **Idempotence de la migration sur une colonne préexistante** : un test/script qui crée `item.statut_autorite` dans son *ancienne* forme `text check(...)`, rejoue ensuite le `model_item.sql` actuel, et vérifie que la colonne se retrouve bien typée `public.statut_autorite_t` (échouerait actuellement — voir §2.1).
- **Suppression d'une ligne `item_bouteille`** : vérifier si `item.date_echeance` est vidée, conservée, ou explicitement documentée comme obsolète (non testé aujourd'hui dans un sens ou l'autre).
- **Scénarios de crash/rejeu concurrent pour `item_bouteille_appliquer_hors_validite()`** : déjà bien couvert pour « rejoué deux fois » (idempotent, 0 ligne au second appel) — envisager aussi un test d'invocation concurrente (deux sessions l'appelant en même temps) pour confirmer l'absence de double-transition/double-ligne d'audit pour le même item, la fonction n'étant pas protégée par un verrou consultatif explicite.
- **`bouteille_type_referentiel` avec une `matiere` hors domaine** (ex. `'titane'`) : vérifier qu'elle se résout aujourd'hui en comportement propagateur de `NULL` (documente le contrat actuel, un peu fragile) ou ajouter le garde-fou du §3.4 et tester qu'elle lève une erreur à la place.
- **Test de parité C# `CylinderReferenceType.Resolve` vs SQL `bouteille_type_referentiel`** pour le cas de matière manquante, une fois le §3.2 tranché dans un sens ou l'autre.

## 6. Refactoring optionnel

Aucun avec une valeur suffisamment claire pour justifier le remous en l'état — le patron de référentiel historisé/append-only, le moteur d'échéance à deux compteurs, et la garde SECURITY DEFINER + `revoke`/`grant` sur la bascule automatique sont tous cohérents avec les conventions existantes du code (`item_transition`, `custom_access_token_hook`) et n'ont pas besoin d'être retravaillés, seulement les correctifs ci-dessus.
